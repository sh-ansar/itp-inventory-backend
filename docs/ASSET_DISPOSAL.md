# Inventory: документированное списание и утилизация имущества

Дата разработки: 31.10.2026. Функция реализована в Laravel API + Vue 3. **Это не юридическая консультация и не проверка ЭЦП/подлинности приказов.** Документы загружаются пользователями и хранятся без автоматической проверки подписей.

## Назначение

Разделяем четыре состояния **заявки** и три состояния **основного средства**:

| Этап заявки | Статус актива | Кто выполняет |
| --- | --- | --- |
| Не создана / `draft` | `active` | `inventory_manager`, `company_admin` создают и редактируют черновик |
| `submitted` | `active` | Менеджер или администратор направляет заявку на согласование |
| `approved` | `written_off` | Только `company_admin` утверждает списание по приказу |
| `disposed` | `disposed` | Только `company_admin` фиксирует физическую утилизацию по акту |

Важное различие: **списание по приказу не равно физической утилизации**, и архивирование технически ошибочной записи не является ни одной из этих операций. Обычный `PUT /assets/{id}` и перемещение `POST /movements` запрещены для списанных и утилизированных активов. `DELETE /assets/{id}` запрещён для имущества с какой-либо заявкой, чтобы исключить обход процесса. Инвентарный номер остаётся зарезервированным.

## Обязательные правила

1. Для создания заявки актив должен быть `active`. На каждый актив может быть не больше одной постоянно сохраняемой заявки (уникальный индекс).
2. Черновик содержит текстовое обоснование (10–2000 символов). Номер/дата приказа на этапе создания могут отсутствовать, но должны быть указаны к моменту отправки.
3. Отправка `draft → submitted` требует **указанный номер и дату приказа** и хотя бы один документ типа `write_off_order`. Отправка без файлов возвращает 422.
4. Администратор может вернуть `submitted → draft` с обязательным объяснением (5–1000 символов). До повторного согласования данные можно исправить; загруженные файлы и события не удаляются.
5. `submitted → approved` изменяет статус актива на `written_off` в **той же транзакции** с журналом актива и заявки. Требуется ожидаемая версия обоих объектов.
6. `approved → disposed` требует файл типа `disposal_act`, номер акта, дату утилизации и способ (`recycling`, `destruction`, `waste_transfer`, `other`). При подтверждении статус актива становится `disposed`.
7. После `disposed` заявки и файлы доступны на чтение, добавлять или менять документы нельзя. Удаления заявки и вложений через UI/API нет.
8. Роль `viewer` и прочие участники компании могут читать заявки, события, скачивать файлы, но не создавать/редактировать/утверждать.
9. Доступ всегда ограничен `company_id`; чужая компания возвращает 404. PostgreSQL ограничивает связи дополнительно составными FK `(id, company_id)`.
10. Все изменения синхронизируются по `version` с HTTP 409 при конфликте. Первой блокируется строка актива, затем строка заявки — единый порядок блокировок для редактирования, архивации, движения и списания.

## Файлы

Документы `write_off_order`, `disposal_act`, `supporting` принимаются в PDF, PNG, JPEG до 5 МиБ. Содержимое проверяется сервером; изображения декодируются и **повторно кодируются как PNG**, чтобы не отдавать неподтверждённые исходные байты. Для PDF проверяется файловый тип и сигнатура `%PDF-`, но **не наличие или корректность подписи**. Содержимое PDF никогда не показывается встроенным HTML-просмотрщиком; оно выдаётся только скачиванием (`Content-Disposition: attachment`, `nosniff`, приватный `Cache-Control`, `CSP sandbox`).

Для каждого файла записываются `sha256`, размер, исходное имя (с очисткой управляющих символов), тип, автор и дата. Сами файлы находятся в приватном диске Laravel (`inventory-disposals/{company_id}/UUID.ext`), а не в публичном `storage/public`. Если сохранение транзакции не прошло, созданный файл удаляется. Контракт GET требует авторизацию участника компании и строгое совпадение заявки, актива и ID файла.

В интерфейсе отображаются документы и их история. Файл допускается загрузить в следующем состоянии: `write_off_order` — черновик; `disposal_act` — утверждённое списание; `supporting` — до завершения утилизации. После завершения файлы не удаляются. Срок хранения и формальная проверка ЭЦП должны отдельно согласовываться с юристами и бухгалтерией.

## API (префикс `/inventory-api/api/v1/companies/{company}`)

| Метод/путь | Результат |
| --- | --- |
| GET `/disposal-cases?status=&search=&page=&per_page=` | Постраничный реестр заявок компании, фильтр этапа и поиск по названию/номеру имущества |
| POST `/assets/{asset}/disposal-case` | Создать черновик (`asset_version, reason, order_number?, order_date?`) |
| GET `/assets/{asset}/disposal-case` | Карточка заявки и документы |
| PUT `/assets/{asset}/disposal-case` | Сохранить черновик (`version, reason, order_number?, order_date?`) |
| POST `/assets/{asset}/disposal-case/submit` | Направить на согласование (`version`) |
| POST `/assets/{asset}/disposal-case/return` | Вернуть на исправление (`version, reason`) |
| POST `/assets/{asset}/disposal-case/approve` | Утвердить (`version, asset_version`) |
| POST `/assets/{asset}/disposal-case/dispose` | Утилизация (`version, asset_version, disposal_act_number, disposal_date, disposal_method`) |
| POST `/assets/{asset}/disposal-case/documents` | Приватная загрузка multipart (`version,document_type,file`) |
| GET `/assets/{asset}/disposal-case/documents/{document}` | Скачать защищённый файл |
| GET `/assets/{asset}/disposal-case/events` | Последние 100 событий заявки |

## Техническое тестирование

- PostgreSQL 16 disposable DB: применение миграции, проверки уникальных индексов, составных FK и CHECK, откат, повторное применение, уничтожение временной БД.
- SQLite in-memory: `AssetDisposalWorkflowTest` проверяет сквозной процесс, права разных ролей и компаний, невозможность двойного списания/утилизации, акт до фактического завершения, немодифицируемый аудит, конфликт версий и безопасность загрузки.
- Vue 3: API-конракт, CSRF, одинаковые RU/EN/GE ключи, TypeScript и production сборка.
- Chromium E2E: заявки от создания до подтверждённой утилизации, скачивание приказа, возврат на доработку, просмотр `viewer`, отсутствие горизонтального переполнения на 360/390/768/1024/1440 px, регрессия инвентаризаций/складов/планов.

## Миграция старой UOS

Интерфейс и операции восстановлены функционально, **реальные старые истории, приказы, электронные подписи и акты не импортированы**: исходный UOS backend и его производственная БД ещё не обследованы и контракт загрузки старых файлов не подтверждён. Перед переносом нужно составить mapping `legacy_company_id + legacy_asset_id → inventory_company_uuid + asset_uuid`, загрузить исторические записи отдельно от живого процесса, сравнить контрольные количества и хэши документов, провести пробный импорт с откатом. Не подменять старые даты текущими и не выдавать перенесённые документы за заново согласованные заявки.

## Релиз и откат

Создать согласованный backup Inventory PostgreSQL и приватных файлов, проверить возможность restore. Вести изолированный деплой Inventory без изменения Portal, HRM, Apache global aliases, общих ключей и других баз. `2026_10_31_000009_asset_disposal_workflow` создаёт только новые таблицы. Не делать rollback после реального начала операций без отдельного решения о сохранении документов и истории; rollback уместен на пустом QA-стенде.
