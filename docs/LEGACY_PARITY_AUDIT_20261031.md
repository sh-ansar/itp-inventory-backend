# Inventory legacy → Vue 3 / Laravel: функциональная сверка (31.10.2026)

## Источники, ограничения

Сверено с исходниками в `sh-ansar/itp-inventory-frontend` (старый Vue 2 код из `src/components`, не `modern`) и текущими `modern/src/pages`, `modern/src/api` и Laravel `routes/api.php`. Функции перечислены только по видимым исходникам, **не по непроверенной живой старой БД**. Оценка статуса: `готово` — новый API+UI+тесты; `частично` — эквивалент не полный; `нет` — новая реализация не обнаружена; `новое` — добавлено вне старых экранов.

## Контракт нового редактора планов

План хранится отдельно от юридического/бухгалтерского местонахождения и от исторических снимков инвентаризаций. План объекта показывает только его непосредственные дочерние помещения и оборудование, назначенное **непосредственно** выбранному узлу. Для оборудования в комнате откройте план этой комнаты; редактирование координат не создаёт фиктивное движение активов. Размещения и размеры сохраняются под optimistic-lock версией плана, с именем автора и неизменяемым журналом событий. Изображения хранятся приватно и выдаются только авторизованному участнику компании.

**Не использовать новый план как «полный план здания» без измеряемой геометрии.** Текущий холст — масштабируемая редакционная схема с произвольными координатами, не CAD/БТИ-план и не GPS. При загрузке фонового плана его пропорции адаптируются к размеру холста; геодезической точности не заявлено.

## Запреты на миграцию без сверки

1. Не считать ID 1С, legacy UOS, HRM и Inventory взаимозаменяемыми. Составить таблицу `source_system + source_id -> target UUID`, проверить количество строк, уникальность, связи.
2. Не переносить рабочие логины/пароли или ключи из HRM и Portal в Inventory.
3. Не удалять старые записи после импорта: сначала read-only сравнение карточек, статусов, расположений, МОЛ, историй, документов, QR; затем тестовый импорт с откатом.
4. Не применять миграции к БД Portal или HRM; Inventory владеет собственными таблицами и сессией.
5. Не запускать самовольную синхронизацию 1С/legacy API на production: только согласованный read-only dry-run, с ограничением нагрузки.

## Приоритеты следующей функциональной миграции

**P0**: инвентарная карточка/статусы; заполняемый реестр с правильными полями; процедура списания с приказами и жизненным циклом; привязка legacy локаций/МОЛ; документы и история; матрица ролей. **P1**: множественные компании в одной проверке, отчёты с PDF/XLSX и вложениями, серверные пользовательские настройки таблиц, пакетная печать QR. **P2**: интеграционный модуль 1С/legacy, настройки и журнал синхронизаций, аналитика, дополнительные складские первичные документы. Для каждого блока: миграция-репетиция, backend feature tests, браузерные сценарии на 4 ширинах, GitHub CI и отдельный rollback.
