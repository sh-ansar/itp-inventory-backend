## Что именно тестировали

Пагинация 25 записей с индексом компании, подсчет активов и substring-поиск в названиях на наборе 10k. Нагрузка осуществлялась на уровне PostgreSQL через pgbench — это НЕ HTTP API тест с авторизацией, не нагрузка экранов и не proof SLA production.

Восстановление проверено на синтетическом снимке. Backup/restore рабочей БД требует отдельного регламента с владельцем данных: ограниченные права, техническое окно, назначенные RPO/RTO, размер WAL, контроль доступа к private storage, порядок recovery и реальная проверка восстановления в независимой среде.

## Повторение без угрозы production

- Запускать только отдельный PostgreSQL 16 экземпляр на loopback 127.0.0.1 с отдельным data dir/port и синтетическими пользователями.
- Проверять host, port, DB_DATABASE, DB_USERNAME в начале каждого скрипта; запрещен 5432 и работа с production.
- Создать отдельную пустую тестовую базу; применить Laravel миграции через конфигурацию local/QA.
- Загрузить 10k синтетических активов; проверить разделение по двум компаниям.
- Запустить pgbench с файлом только SELECT, максимум 20 клиентов, короткая длительность и read-only.
- Сделать pg_dump -Fc; проверять exit code, SHA256 и pg_restore --list; восстановить **только** в новую пустую QA базу.
- Сверить counts, migration journal и детерминированную контрольную сумму состава активов.
- Остановить отдельный QA процесс PostgreSQL; сохранить только отчет/скрипты/QA архив согласно retention.

## Оставшиеся эксплуатационные доказательства

1. HTTP/E2E нагрузки с 20 реальными авторизованными пользователями на изолированном API, проверка API response p95/p99 и ошибок 401/409/419/5xx.
2. Конкурирующие изменения одной карточки: защита version, корректность audit, atomic bulk, отсутствие cross-company foreign key.
3. Производственные RPO/RTO и восстановление рабочей схемы из обезличенной резервной копии с отдельным security approval.
4. Мониторинг роста базы 100k+ активов и индексирование substring-поиска после EXPLAIN/ANALYZE с выбранным workload.

**Вывод:** подготовка нагрузочного и DR стенда, миграции и read-only concurrency/restore закрыты; end-to-end API performance и production DR остаются отдельными release gates, не должны называться завершенными.
